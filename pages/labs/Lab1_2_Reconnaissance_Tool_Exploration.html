nmap Network Scanning

Demonstrating network scanning fundamentals using nmap against authorized targets. You'll perform version detection and script scanning to identify services and potential vulnerabilities.

Why It Matters

Nmap is the industry-standard network scanner. Understanding its capabilities helps both attackers (who use it to map target networks) and defenders (who need to understand what attackers see). Version detection reveals exactly what software is running, which directly informs vulnerability research.

  1. Open a terminal in your Kali VM
  2. Run a version detection scan:
    nmap -sV scanme.nmap.org
    What this does

    Concept: The -sV flag tells Nmap to probe open ports and determine what service and version is running on each one. Without it, Nmap only tells you a port is open. With it, you learn what software is listening (for example, the name and version of the web server or SSH server).

    In your output: Look for the VERSION column in the results table. Each open port should show specific software and version numbers. This information is what makes vulnerability research possible. Check the first line of the report too. The address in parentheses after scanme.nmap.org should not start with 127. If it does, your network’s DNS is sending you back to your own machine and you are scanning your own VM, which is why every port shows closed. Look up the real address with dig +short scanme.nmap.org @8.8.8.8 and scan that address instead.

  3. Note the open ports and service versions detected
  4. Run a default script scan:
    nmap -sC scanme.nmap.org
    What this does

    Concept: The -sC flag runs Nmap’s default set of scripts against discovered services. These scripts perform safe enumeration tasks like grabbing SSH host keys, checking HTTP headers, and detecting common misconfigurations.

    In your output: Compare this to the -sV output. You should see additional details like SSH host keys and HTTP page titles that weren’t in the version scan. Scripts extend Nmap from a port scanner into an information-gathering platform.

  5. Compare the output. What additional information did scripts reveal?
terminal
Key Flags
  • -sV: Version detection
  • -sC: Default scripts
  • -A: Aggressive (combines -sV, -sC, OS detection, traceroute)

netcat Banner Grabbing

Using netcat to manually connect to network services and capture their identification banners: the text services display when you connect.

Why It Matters

Service banners reveal software versions, hostnames, and configuration details. This low-level technique helps verify nmap results and often reveals information automated scanners miss. Netcat is the “Swiss Army knife” of networking.

  1. Connect to SSH port on scanme.nmap.org:
    nc -v scanme.nmap.org 22
    What this does

    Concept: nc (netcat) opens a raw TCP connection to a host and port. The -v flag enables verbose output so you can see the connection status. Port 22 is the standard SSH port.

    In your output: You should see a connection message followed by the SSH banner (a line starting with SSH-2.0- followed by the server software and its version). This banner reveals the exact software version. That is valuable intel for an attacker.

  2. Observe the banner that appears (SSH version string)
  3. Press Ctrl+C to disconnect
  4. Try connecting to port 80:
    nc -v scanme.nmap.org 80
    What this does

    Concept: Port 80 is the standard HTTP port. Unlike SSH, web servers don’t send a banner automatically. You need to send an HTTP request first. This teaches you that different protocols behave differently during reconnaissance.

    In your output: You’ll see a connection confirmation, but no banner yet. You need to type the HTTP request in the next step to get a response.

  5. Type HEAD / HTTP/1.0 and press Enter twice to get HTTP headers
    What this does

    Concept: HEAD / HTTP/1.0 is a raw HTTP request asking the server for headers only (no page content). The response reveals the web server software, version, and sometimes OS details. This is manual banner grabbing for HTTP, exactly what automated tools do behind the scenes.

  • No banner: Some services don’t display banners until you send data

dirb Directory Discovery

Using dirb to brute-force discover hidden directories and files on web servers, finding content that isn’t linked from the main site.

Why It Matters

Web apps often have hidden admin panels, backup files, or development directories. Directory brute-forcing finds these resources that attackers commonly exploit.

lightbulb
Your Target: the NEXUS Training Range

Checkpoints 3 and 4 scan the NEXUS training range, a practice web server that runs on your own VM using the Docker you installed in Lab 1.1. Start it with the first step below. It keeps running until you stop it, so Checkpoint 4 uses the same one. The range hands back a real mix of response codes: some paths return 200, some 403, and missing ones 404. Read its robots.txt too.

  1. Start the NEXUS training range on your VM:
    docker run -d -p 8080:80 --name nexus-range jfnewsom/nexus-range:latest
    What this does

    Concept: -d runs the container in the background, -p 8080:80 makes its web server answer on port 8080 of your VM, and --name gives it a name you can stop it by. Run docker ps and confirm nexus-range shows as Up before you scan.

  2. Run dirb against the range:
    dirb http://127.0.0.1:8080
    What this does

    Concept: dirb sends HTTP requests for thousands of common directory and file names (from a wordlist) and reports which ones exist. It’s a brute-force approach to content discovery: finding pages the site doesn’t link to publicly.

    In your output: Watch for lines showing CODE:200 (the page exists) versus CODE:403 (forbidden but exists) and CODE:301 (redirect). Each discovered path is a potential attack surface.

  3. Watch it test common directory names
  4. Note which return CODE:200 (found)
  5. Let it run or press Ctrl+C after several results
terminal
Wordlist Location

Default wordlists: /usr/share/dirb/wordlists/

What You Should Have

Output showing discovered directories like /admin/, /images/, /cgi-bin/ with HTTP response codes. If you used the NEXUS range instead, expect a mix of accessible and forbidden paths: several directories returning CODE:200, several returning CODE:403, and a robots.txt worth reading. A 403 is a finding, not a failure. It confirms the path is really there, which is exactly what a 404 does not tell you.

warning
  • Forgetting http://: URL must include the protocol (dirb http://target, not just dirb target)
  • Slow scan: Dirb tests thousands of paths; use Ctrl+C after seeing results for training purposes
  • Connection errors: Target site must be reachable; test with curl first if dirb fails

nikto Vulnerability Scanning

Using nikto to scan web servers for known vulnerabilities, misconfigurations, and dangerous files.

Why It Matters

Nikto checks for 6,700+ dangerous files and 1,250+ outdated server versions. It quickly identifies low-hanging fruit that attackers commonly exploit.

lightbulb
Same Target as Checkpoint 3

nikto scans the NEXUS training range you started in Checkpoint 3. If you rebooted or stopped it since, start it again with docker start nexus-range and confirm with docker ps. When nikto finishes, stop and remove the range: docker stop nexus-range, then docker rm nexus-range.

  1. Run nikto against the range:
    nikto -h http://127.0.0.1:8080
    What this does

    Concept: nikto is a web server vulnerability scanner that checks for thousands of known issues: outdated software, dangerous default files, misconfigurations, and insecure headers. The -h flag specifies the target host.

    In your output: Each line prefixed with + is a finding. Look for server version disclosures, missing security headers, and OSVDB reference numbers. These findings would go into a real vulnerability assessment report.

  2. Watch the output: nikto reports findings as it scans
  3. Note types of findings: server info, outdated software, dangerous files
  4. Let it run for a few minutes

  • photo_camera
    12-nikto-results.png Capture nikto output showing findings. Save as 12-nikto-results.png

What You Should Have

Output showing server information, potential vulnerabilities, and interesting files discovered. If you used the NEXUS range instead, expect findings in the same categories: a disclosed server version, a missing security header, a directory with indexing left enabled, and entries in robots.txt flagged for manual review.

warning
  • Wrong port: Use -p 443 for HTTPS targets; nikto defaults to port 80
  • Loud scanning: Nikto is NOT stealthy; every request is logged and easily detected
  • False positives: Verify findings manually; nikto reports potential issues, not confirmed vulnerabilities

searchsploit Vulnerability Research

Using searchsploit to search the Exploit Database for known vulnerabilities and exploits based on software versions discovered during reconnaissance.

Why It Matters

Once you know what software a target runs, you need to research whether known exploits exist. Searchsploit provides offline access to Exploit-DB, the largest public archive of exploits and vulnerable software.

  1. Update the database:
    sudo apt update && sudo apt install --only-upgrade exploitdb
    What this does

    Concept: Searchsploit works offline by searching a local copy of the Exploit Database, which Kali installs as the exploitdb package. Upgrading that package pulls in the latest exploits. New vulnerabilities are published daily, so keeping this current matters. You may see sudo searchsploit -u used for this elsewhere. It updates the same database, but on a fresh Kali install it can also download a separate 2.5 GB archive of papers that this lab does not use.

  2. Search for Apache vulnerabilities:
    searchsploit apache 2.4
    What this does

    Concept: This searches the local Exploit-DB for any exploit matching “apache 2.4.” In a real engagement, you’d take the exact version from your Nmap scan (the server name and version number) and search for known exploits targeting it. This is where reconnaissance becomes actionable.

    In your output: You’ll see a table of matching exploits with titles, types (local, remote, webapps, DoS), and file paths. The path column tells you where the exploit code lives on your system if you need to examine it.

  3. Note the exploit titles, types, and paths
  4. Try searching for OpenSSH:
    searchsploit openssh
    What this does

    In your output: Compare the results to your Apache search. Notice the different exploit types and how the version numbers in the titles help you narrow down which exploits apply to a specific target. In practice, you’d cross-reference these results with the exact version string from your Nmap scan.

team
Both Sides of the Shield
security
What Red Team Learns
  • Reconnaissance is the Foundation: Every engagement starts with information gathering. nmap gives you open ports and versions; netcat confirms banners manually; dirb finds hidden paths; nikto flags known misconfigurations. Together, these six tools build a complete picture of a target’s attack surface.
  • Version Intelligence Drives Exploitation: A version string from nmap or netcat banner grabbing feeds directly into searchsploit. A server name and version number becomes a CVE list. This chain (discover, identify, research) is the core offensive workflow.
  • SMB Is a Username Factory: enum4linux null session enumeration extracts usernames, shares, and password policies without authenticating. That user list becomes your credential attack target.
security
What Blue Team Learns
  • Your Logs Record This Reconnaissance: Every nmap scan, dirb request, and nikto probe leaves traces in access logs. Defenders who run these tools against their own infrastructure know exactly what a scan looks like and can build detection rules accordingly.
  • Version Banners Are Information Leaks: Service banners reveal software versions to anyone who connects. Suppressing banners and obscuring version strings reduces the reconnaissance value an attacker gains from a scan.
  • Authorized Scanning Is Blue Team Work: Running these tools on your own infrastructure before an attacker does is called attack surface management. Everything you discover today, a defender should already know about their own environment.
sync_alt
The Purple Team Connection

The six tools in this lab are used identically by both sides. Red team runs them offensively to map targets. Blue team runs them defensively to audit their own exposure. The difference is authorization and intent, not the tools themselves.
