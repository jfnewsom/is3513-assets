Set Up Your Document

Downloading the Engagement Packet template, opening it in desktop Word, and setting the two document properties that identify it as yours. Five minutes, before you write a word.

Why It Matters

Document mechanics were the single largest avoidable point loss last term, and none of it had anything to do with security knowledge. Nearly all of it traces back to a document set up wrong on day one and never recovered. Do this first and it stays done.

  1. Download the template: EP_M3_GulfCoast.docx. Save it somewhere you will find it again.
  2. Open it in desktop Microsoft Word, not Word for the web, not Google Docs, not Preview. Those cannot create the captions, cross-references and citation fields this packet is graded on. Maximize the window so the ribbon shows labels instead of bare icons.
  3. Turn on the Navigation Pane. Windows: View > Navigation Pane. Mac: View > Sidebar > Navigation. Leave it open for the whole engagement. It is how you catch a broken heading before it reaches the Table of Contents.
  4. Set the Author property. Windows: File > Info, the Author box on the right. Mac: File > Properties… > Summary. Word appends your abc123 to the existing author rather than replacing it. That is expected. Leave it.
  5. Set the abc123 custom property. Windows: File > Info > Properties > Advanced Properties > Custom. Mac: File > Properties… > Custom. It has to match the abc123 hostname visible in your screenshots. Together they are how this packet is tied to the machine that produced its evidence.
  6. Fill in the cover page by hand. Type your name in the Analyst / Student cell and your abc123 in the abc123 (VM ID) cell. Nothing on the cover fills itself in from the document properties.
  7. Save the file now, and keep saving as you go.

What You Should Have

The template open in desktop Word, the Navigation Pane visible down the left, and your abc123 in both the Author field and the abc123 custom property.

Azure Connection & Live Capture

Establish an SSH connection to the Azure-hosted Gulf Coast patient portal and capture the network traffic using Wireshark on your host machine.

Why It Matters

This is your first interaction with real cloud infrastructure. Unlike training PCAPs, this is live traffic to a production-like environment. The skills you practiced in Lab 3.2 now apply to actual client systems. Jennifer Walsh is counting on your analysis to determine if the anomalous traffic her team flagged represents a genuine threat.

Step 1: Prepare Your Capture Environment

  1. Open Wireshark on your host machine (not inside the Kali VM).
  2. Identify your active network interface (Wi-Fi or Ethernet).
  3. Resolve the server’s IP address from a terminal on your host:
    nslookup gulfcoast-portal.southcentralus.cloudapp.azure.com
    What this does

    Concept: nslookup queries the Domain Name System (DNS) to translate a hostname into an IP address, the same process your browser performs behind the scenes every time you visit a website.

    In your output: Look for a line showing Address: followed by an IP (e.g., 104.215.116.139). This is the IP you’ll use in your Wireshark capture filter.

  4. Start a Wireshark capture on your active interface with a capture filter using the IP from nslookup:
    host 104.215.116.139
    (replace with the IP nslookup returned)
What this does

Concept: Wireshark’s capture filters (BPF filters) resolve hostnames once at capture start and can silently fail. Using the IP directly is more reliable and is standard professional practice. You’ll still use the FQDN for SSH and browser connections. Only the capture filter needs the IP.

Step 2: Connect to Azure VM

  1. Open a terminal in your Kali VM.
  2. SSH to the Gulf Coast portal:
    ssh student@gulfcoast-portal.southcentralus.cloudapp.azure.com
    What this does

    Concept: SSH (Secure Shell) creates an encrypted tunnel between your Kali VM and the remote server. All traffic within the tunnel is encrypted, which is why Wireshark will show SSH packets but cannot read their contents.

    In your output: You’ll be asked to accept the host key fingerprint (type yes), then prompted for a password. After successful login, you’ll see a welcome banner identifying the Gulf Coast Healthcare Partners portal server.

    Flags:

    • student: The username to authenticate as on the remote server
    • @: Separates the username from the hostname
    • gulfcoast-portal...cloudapp.azure.com: The FQDN (Fully Qualified Domain Name) of the Azure-hosted server
  3. Password: NEXUSanalyst2026! (case-sensitive). Accept the host key fingerprint when prompted.

Step 3: Activity A: Browse via HTTPS

  1. Open Firefox in your Kali VM and navigate to:
    https://gulfcoast-portal.southcentralus.cloudapp.azure.com
  2. Accept the certificate warning when prompted. This is a finding you will document.
  3. Interact with the page (click links, explore).

Step 3: Activity B: Browse via HTTP

  1. In the same browser, navigate to the HTTP version:
    http://gulfcoast-portal.southcentralus.cloudapp.azure.com
  2. Notice anything different about how the site responds? Document your observation.

Step 3: Activity C: Reconnaissance from Kali

  1. In your Kali VM (a separate terminal from your SSH session), request the HTTP headers:
    curl -I http://gulfcoast-portal.southcentralus.cloudapp.azure.com
    What this does

    Concept: curl is a command-line tool for making HTTP requests. In security assessments, it’s preferred over a browser because it shows the raw server response without client-side rendering or caching. Examining response headers is one of the first steps in web application reconnaissance.

    In your output: You’ll see headers like Server:, Content-Type:, and others. Pay close attention: what information is the server revealing about itself that an attacker could use?

    Flags:

    • -I: HEAD request: retrieves only the response headers, not the page content. Less noisy than a full GET request and reveals server configuration details.
  2. Now request the HTTPS headers for comparison:
    curl -k -I https://gulfcoast-portal.southcentralus.cloudapp.azure.com
    What this does

    Concept: The same request but over HTTPS (encrypted). Comparing HTTP and HTTPS responses side-by-side can reveal configuration differences. Servers sometimes expose different headers depending on the protocol.

    In your output: Compare this response carefully to the HTTP version. Do you see any headers here that were not present in the HTTP response? Any differences are potential security findings.

    Flags:

    • -k: Insecure mode: tells curl to skip certificate verification. Required here because the server uses a self-signed certificate not trusted by default.
    • -I: HEAD request: headers only, same as before.

Step 3: Activity D: Server Exploration via SSH

  1. In your SSH session, list the web server’s document root:
    ls /var/www/
    What this does

    Concept: /var/www/ is the default web root on Linux servers. Listing its contents shows what web applications and directories the server hosts.

    In your output: You should see one or more directories. Note the names. Do any suggest older or legacy systems that might have weaker security controls?

  2. Check for Gulf Coast application files:
    ls /opt/gulfcoast-*
    What this does

    Concept: /opt/ is where third-party and custom applications are typically installed. The wildcard (*) matches any file or directory starting with gulfcoast-.

    In your output: Any files or directories here represent installed Gulf Coast applications. Explore their contents for configuration files, logs, or other artifacts.

  3. Examine the web server configuration:
    cat /etc/nginx/sites-enabled/*
    What this does

    Concept: /etc/nginx/sites-enabled/ contains active site configurations for the nginx web server. Reading these files reveals how the server is configured: ports, SSL/TLS settings, served locations, and security headers (or lack thereof).

    In your output: This is a goldmine for your assessment. Read carefully: look for SSL protocol versions, enabled locations, header settings, and misconfigurations. Many findings you’ll document in your report can be confirmed right here.

Step 4: Verify Your Capture

  1. In Wireshark, go to Statistics → Protocol Hierarchy.
  2. Verify you have at minimum: SSH (from terminal session), HTTP (from unencrypted browsing), TLS (from HTTPS browsing).
  3. If you only see one protocol, complete the activities you missed before stopping.
  4. Once verified, stop the capture and save as gulfcoast-live-capture.pcap.

lightbulb

An empty capture almost always means Wireshark is watching the wrong place, or nothing was sent while it was running. Even if the portal were down or your network blocked SSH, Kali’s connection attempts would still show up as packets. Work through these in order:

  1. Filter in the right box. host 104.215.116.139 is a capture filter. It goes in the “...using this filter” bar on the Wireshark welcome screen, above the interface list, before you start. It turns green when it’s valid. The display filter bar at the top of the capture window uses different syntax, so the same filter turns red there; the display filter version is ip.addr == 104.215.116.139.
  2. Right interface. Pick the interface with the moving sparkline: your real Wi-Fi or Ethernet adapter. Not loopback, a virtual machine adapter or a VPN adapter.
  3. VPN off. If a VPN is running on your host, your traffic leaves through the tunnel, and your Wi-Fi interface only sees encrypted packets going to the VPN server.
  4. Start the capture first, then generate the traffic. Wireshark only records what happens after you press start. With the capture running, do the SSH connection, the Firefox visits and the curl commands. With this filter, an idle capture stays empty.
Quick test: with the capture running, run curl -I http://gulfcoast-portal.southcentralus.cloudapp.azure.com from the host terminal where you ran nslookup. If packets show up, your filter and interface are good and the problem is on the Kali side. If nothing shows up, it is still one of the four above. Either way, stop and restart the capture before your real run, so the pcap holds only the lab traffic. If SSH from Kali fails right away with “could not resolve hostname,” Kali itself has no network connection, which is a different fix: post the error in Discord.

lightbulb

Prove you could reach it; don’t take it. Unless the client has authorized it in writing, document that the files exist, where they live, how you got to them and what they are. A directory listing (ls -la) showing names, sizes and timestamps is usually enough evidence. Copying sensitive data off a client’s system means NEXUS is now holding data it was never supposed to have. Exposed sensitive data is a finding, and on a real engagement it usually gets a same-day call to the client. If you show any file contents as evidence, redact the sensitive details. If you already downloaded something, say so in your Methodology and Runbook, note that you deleted your copies, and delete them.

warning
  • VPN blocking SSH: If you can’t connect, disable any VPN on your host machine first. Some campus networks also block outbound port 22; try from a mobile hotspot.
  • Wrong interface: Wireshark runs on your HOST machine; all other activities (browsing, SSH, curl) happen inside your Kali VM
  • Firewall issues: Some campus networks block outbound SSH (port 22); try from a mobile hotspot
  • Password typo: Password is case-sensitive: NEXUSanalyst2026!

Clean Up and Submit

Walking the finished packet end to end, refreshing everything Word computes for you, and stripping out everything that was only ever scaffolding. Ten minutes.

Why It Matters

Every deduction in this category is avoidable and none of it is about security. A packet that goes out with placeholder text still in it, a Table of Contents that describes an earlier draft, or a figure number that points at the wrong picture tells the client nobody read the document before sending it. They will wonder what else nobody checked.

  1. Refresh every field. Windows: Ctrl+A then F9. Mac: ⌘A then F9. If nothing happens, your function keys are set to media controls; hold Fn as well, or use the Fn Lock key.
  2. Rebuild the Table of Contents. Right-click it and choose Update Field > Update entire table. Not ‘page numbers only’. That will not pick up sections you added or removed.
  3. Read the Navigation Pane top to bottom. No blank entries. No figure captions. Only real sections. A blank entry means an empty paragraph is carrying a heading style. Click in it and apply Home > Styles > Normal. A caption in the list means it was formatted by hand instead of with Insert Caption.
  4. Compare the Table of Contents against the Navigation Pane. They read from the same source, so they should match exactly. If they disagree, you did not update the entire table.
  5. Click every figure number and every reference to a figure. A real field shades gray when your cursor enters it; typed text does nothing. Anything that does not shade gray was typed by hand and will be wrong the moment something moves. Replace it with References > Insert Caption or References > Cross-reference.
  6. Rebuild the reference list. Click it and press F9, or run References > Bibliography again. Count the entries: you need ten besides the textbook, and every one of them has to appear at least once in the body of the packet. A source that sits in the list and is never cited does not count.
  7. Replace or delete EVERY item in square brackets. Not most of them: all of them. The template ships with roughly 84 bracketed slots: some are places your content goes, some are prompts telling you what belongs there, and both are scaffolding that must be gone before you submit. Search for the bracket character itself. Windows: Ctrl+F. Mac: ⌘F. Type a single [ and step through every hit. Replace it with your own work, or delete the line entirely if that section does not apply. Then search again and confirm you get zero results. The runbook skeleton and the finding card are where they hide.
  8. Check your document properties survived. Windows: File > Info. Mac: File > Properties…. Your abc123 in the Author field and in the abc123 custom property, matching the abc123 hostname visible in your screenshots.
  9. Look at every screenshot at full size. Legible, cropped to what matters, abc123 visible in the prompt. A screenshot nobody can read is evidence of nothing.
  10. Save as .docx and submit that. Word format only, not PDF, not Pages, not Google Docs. The file’s metadata is part of how submissions are verified, and exporting to another format destroys it.
  11. Open what you submitted. Right after you upload, open your submission in Canvas and click the file to preview it. Make sure it’s your finished Engagement Packet for this lab, not the assignment sheet, not the blank template, and not a previous lab’s packet. Canvas’s preview sometimes shows Table of Contents page numbers that don’t match your file. That is the preview, not your document, and packets are graded in Word.
