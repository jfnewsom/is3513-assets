Hash File Setup & Format Analysis

Downloading and analyzing Alamo’s plant-floor Linux password hashes, identifying the SHA-512 crypt format and understanding how salting differs from NTLM.

Why It Matters

Understanding hash formats is essential before attacking them. SHA-512 crypt includes visible salt values that NTLM lacks entirely. This structural difference has major security implications.

  1. Download alamo-plant-hashes.txt: click here to download, then move it to your ~/lab4 directory
  2. Examine the hash file contents:
    cat ~/lab4/alamo-plant-hashes.txt
    What this does

    Concept: cat displays the full contents of the Alamo plant-floor hash file. Compare what you see here to the Alamo corporate NTLM hashes from Lab 4.1. The format is dramatically different.

    In your output: You should see entries in username:$6$SALT$HASH format. The $6$ prefix identifies SHA-512 crypt. Notice each entry includes a unique salt between the second and third $ characters. This is the key architectural difference from NTLM.

  1. Isolate a single entry to analyze the format structure:
    head -1 ~/lab4/alamo-plant-hashes.txt
    What this does

    Concept: head -1 displays only the first line of a file. Isolating one entry makes it easier to break down the format structure without visual clutter.

    In your output: Identify three components: the algorithm identifier ($6$ = SHA-512), the per-user salt (random characters between the second and third $), and the hash itself. This embedded metadata means the system knows exactly how to verify each password, and each user’s hash is unique even if two users share the same password.

John the Ripper Attack

Executing a dictionary attack against Alamo Industries’ SHA-512 hashes using John the Ripper, documenting the dramatically slower crack speed.

Why It Matters

The speed difference you’re about to witness is the entire point of modern password hashing. SHA-512 with salting and rounds is designed to be computationally expensive: what took seconds against NTLM may take hours here. This is defensive design in action, and understanding it helps you explain to clients why algorithm choice matters for their security posture.

“Patience. SHA-512 won’t fall as fast as NTLM. Go get coffee. On a real engagement, we’d let this run overnight. The speed difference isn’t a bug. It’s the whole point of modern password hashing.”

Maya Rodriguez
Senior Penetration Tester, NEXUS Security
  1. Run John the Ripper against the SHA-512 hashes:
    john --wordlist=/usr/share/wordlists/rockyou.txt ~/lab4/alamo-plant-hashes.txt
    What this does

    Concept: Same tool, same wordlist as Lab 4.1, but a completely different experience. John auto-detects the $6$ prefix as sha512crypt format. No --format flag needed because the hash format is self-identifying (unlike NTLM’s raw hex).

    In your output: The speed difference will be dramatic. Where NTLM showed millions or billions of H/s, expect only thousands of H/s here. This is SHA-512 working as designed: the algorithm is deliberately slow to make brute-force attacks computationally expensive. Record John’s c/s rate carefully for your Lab 4.1 vs 4.2 comparison.

  1. Check progress while John is running:
    john --status
    What this does

    Concept: SHA-512 attacks take much longer than NTLM. The --status flag shows progress: candidates tested, current speed, and estimated time remaining. You can also press any key during a running session to get a live status update. If nothing has cracked quickly, don’t wait it out: something is probably misconfigured. This is the defensive value of strong hash algorithms in action. John doesn’t print H/s. Press any key while it runs (or run john --status) and its status line shows four rates: g/s (passwords cracked per second), p/s (candidate passwords tried per second), c/s (hashes computed per second) and C/s (candidate and hash combinations per second). Record c/s: hashes computed per second is John’s equivalent of Hashcat’s H/s.

  1. Display all cracked passwords:
    john --show ~/lab4/alamo-plant-hashes.txt
    What this does

    Concept: The --show flag retrieves cracked passwords from John’s potfile. You may find that fewer accounts were cracked than in Lab 4.1, even with the same wordlist. This is because the slower hash speed means John couldn’t test as many candidates in the same time window.

    In your output: Document which accounts cracked and which resisted; this difference is the core of your engagement report analysis.

Hashcat Attack

Executing the same dictionary attack using Hashcat with mode 1800 (sha512crypt), comparing speed and results to John.

Why It Matters

Hashcat can leverage GPU acceleration, but even with GPU power, SHA-512 crypt remains dramatically slower than NTLM. This demonstrates that algorithm choice matters more than hardware.

  1. Run Hashcat against the SHA-512 hashes:
    hashcat -m 1800 -a 0 -D 1 --username ~/lab4/alamo-plant-hashes.txt /usr/share/wordlists/rockyou.txt
    What this does

    Concept: -m 1800 sets Hashcat to sha512crypt mode (compare to -m 1000 for NTLM in Lab 4.1). -a 0 runs a straight dictionary attack. -D 1 forces CPU mode since VMs typically lack GPU passthrough. --username tells Hashcat the file has a username field to skip; without it the line does not parse and you get a token length exception. Unlike Lab 4.1, no need to extract hashes with cut first.

    In your output: Watch the Speed.#1 line. Compare it to Lab 4.1’s NTLM speed. The difference will be orders of magnitude. GPU acceleration provides minimal benefit for SHA-512 because the algorithm is designed to be memory-hard, not just compute-hard.

  1. Display cracked results:
    hashcat -m 1800 --username ~/lab4/alamo-plant-hashes.txt --show
    What this does

    Concept: The --show flag displays cracked hashes from Hashcat’s potfile. Compare the number of cracked accounts to John’s results; they should be similar since both used the same wordlist against the same hashes. Any differences indicate where one tool continued running longer or used different cracking strategies.

security
What Blue Team Learns
  • Defensive Architecture: Hash algorithm choice has massive security impact: SHA-512 is roughly 100,000x slower to crack than NTLM.
  • Shared Account Risk: Cannot enforce individual accountability with shared credentials.
  • Legacy Debt: Old accounts accumulate risk over time. Regular password audits prevent “common knowledge” passwords.

Results Analysis & Platform Comparison

Compiling your cracking results into two structured tables: an 8-account summary for the Alamo plant floor and a 4-cell platform comparison showing NTLM vs. SHA-512 speeds across both tools. These tables are the analytical core of your Module 4 Engagement Packet.

Why It Matters

Raw terminal output is not a deliverable. Organized findings are. A results table tells the client which accounts are compromised and which credentials are still protecting access. A speed comparison table gives you the concrete numbers to explain why algorithm choice matters, not just that it does.

“Elena’s been fighting this battle internally for three years. Your results table gives her something she can put in front of Frank: names, accounts, and passwords in plain language. That’s how you make the technical case to a non-technical audience. The speed numbers make the architecture case. You need both.”

Carmen Vega
Principal Security Consultant, NEXUS Security
  1. Retrieve your final cracked results from both tools:
    john --show ~/lab4/alamo-plant-hashes.txt && echo '---' && hashcat -m 1800 --username ~/lab4/alamo-plant-hashes.txt --show
    What this does

    Concept: Running both --show commands back-to-back gives you a single terminal view of all cracked credentials from both tools. The results should largely overlap since both used rockyou.txt against the same hashes. Any differences indicate one tool ran longer or the potfiles diverged.

    In your output: You should see username:password pairs for each cracked account. Note which of the 8 Alamo accounts remain uncracked: these are accounts where the password was not in rockyou.txt within your session’s time window.

  2. Build your 8-account results table. Use printf to format it neatly in the terminal:
    printf "%-18s %-20s %-16s\n" "Username" "Password" "Account Type" && printf "%-18s %-20s %-16s\n" "------------------" "--------------------" "----------------"
    What this does

    Concept: printf with fixed-width format strings (%-18s = left-align in 18 characters) creates clean columnar output. You’ll add one row per account manually below this header.

    In your output: A formatted table header. You’ll fill in each of the 8 Alamo plant-floor accounts: username, the cracked password (or not cracked), and the account type (individual, shared, or service). Reference Elena Vasquez’s notes in the lab header: she flagged which accounts are shared floor accounts vs. service accounts.

  3. Below the header, add a row for each of the 8 accounts using the pattern:
    printf "%-18s %-20s %-16s\n" "[username]" "[password or not cracked]" "[account type]"
    What this does

    Concept: Repeat this command for each account, substituting in your actual results. Account types to use: Individual (personal employee account), Shared (multiple users share the credential), Service (application or process account, not a human user). You can find account type information in the hash file comments or from context in the lab narrative.

    In your output: A completed 8-row table. When all rows are printed, your terminal should show a clean, readable summary of all Alamo Industries accounts and their cracking status.

purple
team
Both Sides of the Shield
security
What Red Team Learns
  • Salt Annoyance, Not Defense: Per-user salts defeat rainbow tables but don’t stop targeted cracking; one weak password in a /etc/shadow dump is still one cracked credential, and OSINT-informed wordlists work as well on Linux as they do on Windows
  • Service Account Hunting: Shared accounts and service accounts are softer targets than user passwords: they’re rarely rotated, often shared by multiple admins, and frequently use passwords that match the function (jenkins, mysql, www-data)
  • When SHA-512 Isn’t Slow Enough: Time-per-hash matters more than algorithm name: a single weak password cracks in minutes regardless of SHA-512, while bcrypt or Argon2 with proper work factors push that to days or weeks
security
What Blue Team Learns
  • Algorithm Buys Time: SHA-512 with salt and rounds is a legitimate defensive win: same weak password that cracks in seconds on NTLM may take hours on Linux, giving detection systems room to catch credential exfiltration before damage spreads
  • Shared Accounts Are Audit Findings: Production-floor shared accounts and unrotated service accounts erode every other control; flag them as compliance findings and require either named accounts with audit trails or vaulted secrets with checkout logging
  • Modernize Where It Matters: SHA-512 is the Linux default but bcrypt, scrypt, and Argon2 are stronger; prioritize migration for systems handling privileged credentials, customer authentication, and anything subject to compliance review
sync_alt
The Purple Team Connection

Comparing Windows NTLM and Linux SHA-512 cracking reveals how defensive architecture choices affect attacker timelines. A red-team analyst targeting an NTLM environment can crack credentials in seconds; the same weak password takes orders of magnitude longer on SHA-512. This doesn't mean Linux is invulnerable: weak passwords and shared accounts erode the protection that salting and key-stretching provide. The takeaway for defenders is that algorithm choice buys time, but only password quality and access controls close the gap entirely.
