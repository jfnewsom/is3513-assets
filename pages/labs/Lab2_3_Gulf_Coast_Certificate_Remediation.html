Overview

Gulf Coast Healthcare Partners has a critical problem: their patient portal’s SSL certificate expired, and HIPAA auditors from the Office for Civil Rights (OCR) are arriving in six units. An expired certificate means browsers can no longer confirm patients are talking to the real portal, it teaches them to click through security warnings, and it tells auditors nobody was watching the expiration dates. Your job is to diagnose the certificate issue, remediate it properly, and document everything for the audit trail.

“Before you touch anything, document the current state. Auditors want before-and-after evidence. Every screenshot tells a story: the story of due diligence, proper procedures, and professional remediation.”

Maria Delgado, PhD
Security Compliance Specialist, NEXUS Security

Client Context

Gulf Coast Healthcare Partners: A regional healthcare network headquartered in Houston, Texas. Two years ago, they suffered a ransomware attack that forced a complete infrastructure rebuild.

  • Jennifer Walsh, CISO: “The OCR audit is in 6 weeks. I need this portal working and documented before they arrive.”
  • Thomas Kowalski, VP Infrastructure: “I set this up five years ago when we were half this size. I know it needs updating.”
  • Angela Washington, Privacy Officer: “If PHI travels over that portal unencrypted, we have a reportable breach.”

Assignment Objectives

  • Deploy the Gulf Coast patient portal Docker container and diagnose the certificate issue
  • Generate a new Certificate Signing Request (CSR) and sign it with the existing CA
  • Install the new certificate and verify HTTPS functionality is restored
  • Compile all Module 2 work into a professional Engagement Packet

Key Concepts

  • Certificate Lifecycle: X.509 certificate validity windows, expiration detection, and why expired certificates are a HIPAA compliance failure, not just a browser warning.
  • Certificate Signing Requests: Generating a CSR from an existing private key: the standard PKI workflow for renewal without regenerating keys or disrupting the trust chain.
  • CA Signing Operations: Using the Certificate Authority to sign a CSR and issue a new certificate with a 365-day validity window, the chain of trust in practice.
  • Before/After Evidence: Documenting the broken state before making changes. Auditors require proof of the problem, not just proof of the fix.
  • Engagement Packet Compilation: Assembling three units of work into a single professional deliverable: the Part I (Internal Packet) and Part II (Client Deliverable) structure used by NEXUS Security for all client engagements.

Why It Matters

Document mechanics were the single largest avoidable point loss last term, and none of it had anything to do with security knowledge. Nearly all of it traces back to a document set up wrong on day one and never recovered. Do this first and it stays done.

  1. Download the template: EP_M2_GulfCoast.docx. Save it somewhere you will find it again.
  2. Open it in desktop Microsoft Word, not Word for the web, not Google Docs, not Preview. Those cannot create the captions, cross-references and citation fields this packet is graded on. Maximize the window so the ribbon shows labels instead of bare icons.
  3. Turn on the Navigation Pane. Windows: View > Navigation Pane. Mac: View > Sidebar > Navigation. Leave it open for the whole engagement. It is how you catch a broken heading before it reaches the Table of Contents.

  5. Set the abc123 custom property. Windows: File > Info > Properties > Advanced Properties > Custom. Mac: File > Properties… > Custom. It has to match the abc123 hostname visible in your screenshots. Together they are how this packet is tied to the machine that produced its evidence.
  6. Fill in the cover page by hand. Type your name in the Analyst / Student cell and your abc123 in the abc123 (VM ID) cell. Nothing on the cover fills itself in from the document properties.
  7. Save the file now, and keep saving as you go.

Deploy Container and Diagnose

Deploying the Gulf Coast patient portal container and documenting the broken state before making any changes.

Why It Matters

HIPAA requires documentation of security incidents and remediation. “Before” evidence proves due diligence for auditors. If you fix it first and document after, you have no proof of what the original problem was.

Part A: Deploy the Gulf Coast portal container

  1. Create a working directory for this engagement:
    mkdir -p ~/lab2-gulfcoast
  2. Change into your working directory:
    cd ~/lab2-gulfcoast
  3. Pull and start the Gulf Coast patient portal container:
    sudo docker run -d -p 443:443 -p 2222:22 --name gulfcoast-portal jfnewsom/gulfcoast-portal
    What this does

    Concept: This downloads and starts a Docker container simulating Gulf Coast’s patient portal: an Apache web server with a deliberately expired SSL certificate.

    In your output: Docker prints a long container ID. Give the portal a few seconds to start before you open Firefox. If Docker reports port is already allocated, Brazos from EP 1 is still running and holding port 443. Run docker stop brazos, then docker rm gulfcoast-portal (the failed run left a container with that name), then run this line again.

    Flags:

    • -d: Run in background (detached mode)
    • -p 443:443: Map HTTPS port from container to host
    • -p 2222:22: Map SSH to port 2222 so it doesn’t conflict with your Kali SSH service
    • --name gulfcoast-portal: Assign a friendly name for later docker commands
    • jfnewsom/gulfcoast-portal: The Docker Hub image to pull

Part B: Document the broken state

  1. Open Firefox and navigate to https://localhost. You should see Warning: Potential Security Risk Ahead. Click Advanced. The error code is SEC_ERROR_UNKNOWN_ISSUER: Firefox doesn’t trust Gulf Coast’s internal CA, and it reports that problem first. The expiration is there too, but Firefox only shows it on the certificate itself. Click View Certificate and find the Validity section. The Not After date is in the past. This is your “before” evidence.
  1. Check the certificate dates from your Kali terminal:
    openssl s_client -connect localhost:443 </dev/null 2>/dev/null | openssl x509 -noout -dates
    What this does

    Concept: This connects to the HTTPS server like a browser would, grabs the certificate, and displays its validity dates. The notBefore and notAfter dates tell you when the certificate was issued and when it expired.

    In your output: The notAfter date should be in the past, confirming the certificate has expired.

    Flags:

    • </dev/null: Gives s_client nothing to send, so it hangs up as soon as it has the certificate. Without it, the terminal sits for about 20 seconds waiting for you to type
    • 2>/dev/null: Suppresses noisy connection info
    • -noout: Prevents printing the raw certificate
    • -dates: Shows only the validity period

Certificate Remediation

Generating a new CSR using the existing private key, signing it with the CA, and installing the new certificate.

Why It Matters

Certificate renewal is one of the most common PKI operations you’ll perform. Understanding the CSR workflow (using the existing private key to generate a new request, then signing with the CA) ensures continuity without regenerating keys.

“The README in the PKI directory is your roadmap. Real infrastructure always has documentation (sometimes outdated, sometimes incomplete) but always your starting point. Read it before you touch anything.”

Maria Delgado, PhD
Security Compliance Specialist, NEXUS Security

Part A: SSH into the container and explore the PKI structure

  1. SSH into the Gulf Coast portal container (password: nexus2026):
    ssh -p 2222 student@localhost
  2. Navigate to the PKI directory and read the documentation:
    cd /opt/gulfcoast-pki
  3. Read the README left by the previous administrator:
    cat README.txt
  4. Explore the directory structure:
    ls -la CA/ certs/ csr/
    What this does

    Concept: You’re mapping the PKI infrastructure before making changes. The CA/ directory holds the root Certificate Authority (ca.crt and ca.key). The certs/ directory holds the server certificates including the expired portal.crt. The csr/ directory is your working space for new certificate signing requests.

    In your output: Note the file permissions. The CA key (ca.key) is root-owned for security, while the certs/ directory is student-owned so you can write new files there.

Part B: Generate a new Certificate Signing Request (CSR)

  1. Generate a new CSR using the existing private key:
    openssl req -new -key certs/portal.key -out csr/portal-new.csr -subj "/C=US/ST=Texas/L=Houston/O=Gulf Coast Healthcare Partners/OU=Patient Services/CN=portal.gulfcoasthealthcare.org"
    What this does

    Concept: A Certificate Signing Request (CSR) is a formal application for a new certificate. It contains your public key and identity information, signed with your private key to prove ownership. The CA uses this to issue a new certificate without ever needing your private key.

    Flags:

    • req -new: Create a new CSR
    • -key certs/portal.key: Use the existing private key (no need to regenerate)
    • -out csr/portal-new.csr: Output file for the CSR
    • -subj: Provides identity fields inline (C=country, ST=state, L=locality, O=organization, OU=organizational unit, CN=common name). These are the values in the README’s renewal procedure, and the CN is the portal’s hostname

Part C: Sign the CSR with the Certificate Authority

  1. Sign the CSR using the CA certificate and key (requires sudo because the CA key is root-owned). The paths are relative, so run this from /opt/gulfcoast-pki. If you reconnected since Part A, cd /opt/gulfcoast-pki first, or you’ll get Could not open file or uri for loading CA certificate from CA/ca.crt:
    sudo openssl x509 -req -in csr/portal-new.csr -CA CA/ca.crt -CAkey CA/ca.key -CAcreateserial -out certs/portal-new.crt -days 365 -sha256
    What this does

    Concept: The CA “signs” your CSR by combining your identity and public key with the CA’s digital signature. Anyone who trusts the CA can now verify your certificate is legitimate. This is the chain of trust in action.

    In your output: You’ll see “Certificate request self-signature ok” followed by the subject line. The sudo password is nexus2026.

    Flags:

    • x509 -req: Process a CSR into a signed certificate
    • -CA / -CAkey: Specify the signing Certificate Authority and its key
    • -CAcreateserial: Generate a unique serial number for this certificate
    • -days 365: Set one-year validity period
    • -sha256: Use modern hashing algorithm for the signature

Part D: Install the new certificate

  1. Copy the new certificate into Apache’s SSL directory:
    sudo cp /opt/gulfcoast-pki/certs/portal-new.crt /etc/ssl/certs/portal.crt

  1. Refresh every field. Windows: Ctrl+A then F9. Mac: ⌘A then F9. If nothing happens, your function keys are set to media controls; hold Fn as well, or use the Fn Lock key.
  2. Rebuild the Table of Contents. Right-click it and choose Update Field > Update entire table. Not ‘page numbers only’. That will not pick up sections you added or removed.
  3. Read the Navigation Pane top to bottom. No blank entries. No figure captions. Only real sections. A blank entry means an empty paragraph is carrying a heading style. Click in it and apply Home > Styles > Normal. A caption in the list means it was formatted by hand instead of with Insert Caption.
  4. Compare the Table of Contents against the Navigation Pane. They read from the same source, so they should match exactly. If they disagree, you did not update the entire table.
  5. Click every figure number and every reference to a figure. A real field shades gray when your cursor enters it; typed text does nothing. Anything that does not shade gray was typed by hand and will be wrong the moment something moves. Replace it with References > Insert Caption or References > Cross-reference.
  6. Rebuild the reference list. Click it and press F9, or run References > Bibliography again. Count the entries: you need ten besides the textbook, and every one of them has to appear at least once in the body of the packet. A source that sits in the list and is never cited does not count.
  7. Replace or delete EVERY item in square brackets. Not most of them: all of them. The template ships with roughly 84 bracketed slots: some are places your content goes, some are prompts telling you what belongs there, and both are scaffolding that must be gone before you submit. Search for the bracket character itself. Windows: Ctrl+F. Mac: ⌘F. Type a single [ and step through every hit. Replace it with your own work, or delete the line entirely if that section does not apply. Then search again and confirm you get zero results. The runbook skeleton and the finding card are where they hide.
  8. Check your document properties survived. Windows: File > Info. Mac: File > Properties…. Your abc123 in the Author field and in the abc123 custom property, matching the abc123 hostname visible in your screenshots.
  9. Look at every screenshot at full size. Legible, cropped to what matters, abc123 visible in the prompt. A screenshot nobody can read is evidence of nothing.
  10. Save as .docx and submit that. Word format only, not PDF, not Pages, not Google Docs. The file’s metadata is part of how submissions are verified, and exporting to another format destroys it.
  11. Open what you submitted. Right after you upload, open your submission in Canvas and click the file to preview it. Make sure it’s your finished Engagement Packet for this lab, not the assignment sheet, not the blank template, and not a previous lab’s packet.
